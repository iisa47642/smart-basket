## Первый запуск

На Ubuntu/Debian запустите `sudo ./deploy.sh`. При первом запуске создаются случайный пароль БД и начальный пароль администратора в `.env` с правами 600. Не копируйте этот файл в Git или отчёт. Существующая учётная запись не получает новый пароль при перезапуске. Локальный вариант без установки Docker: `.env.example` → `.env`, заменить обе заглушки паролей, затем `docker compose up -d --build`.

Для локальной демонстрации можно использовать `HTTP_PORT=127.0.0.1:18080`. Для публичного входа настройте HTTPS до передачи пароля через сеть.

## HTTPS для IP-адреса и домена

1. В облачной группе безопасности разрешите 80/tcp и 443/tcp из интернета. SSH 22/tcp оставьте доступным для администрирования. На Ubuntu: `sudo ufw allow 80/tcp` и `sudo ufw allow 443/tcp`.
2. Из каталога уже запущенного проекта выполните `sudo bash scripts/enable-https.sh ПУБЛИЧНЫЙ_IP`. Скрипт запрашивает сертификат Let’s Encrypt через Certbot 5.4, временно освобождая порт 80, и возвращает frontend даже при неудачной проверке. Выпуск включает согласие с условиями Let’s Encrypt; контактный email не регистрируется.
3. Необязательный второй аргумент добавляет домен в тот же сертификат: `sudo bash scripts/enable-https.sh ПУБЛИЧНЫЙ_IP ДОМЕН`. Домен должен указывать на этот сервер. Для текущего размещения используется `13-143-160-190.sslip.io`, который автоматически разрешается в `13.143.160.190`.
4. Откройте `https://ПУБЛИЧНЫЙ_IP/` или HTTPS-адрес домена. Проверьте сертификат, перенаправление с HTTP и работу входа.
5. Проверьте автоматическое продление:

```bash
sudo systemctl list-timers smart-basket-cert-renew.timer
sudo docker run --rm \
  -v /etc/letsencrypt:/etc/letsencrypt \
  -v /var/lib/letsencrypt:/var/lib/letsencrypt \
  -v /var/www/certbot:/var/www/certbot \
  certbot/certbot:v5.4.0 renew --dry-run --webroot -w /var/www/certbot
```

Сертификаты для IP краткосрочные. Служба продления проверяет их дважды в сутки и перечитывает конфигурацию Nginx. Примеры systemd рассчитаны на `/opt/smart-basket`; при другом пути измените WorkingDirectory. При неудаче продления изучите `journalctl -u smart-basket-cert-renew.service`.

HTTPS-конфигурация находится в `docker-compose.https.yml`. Она включает Secure cookie. `deploy.sh` выбирает её автоматически при наличии сертификата. Для ручных операций frontend/backend в HTTPS-среде используйте оба compose-файла:

```bash
sudo docker compose -f docker-compose.yml -f docker-compose.https.yml ps
sudo docker compose -f docker-compose.yml -f docker-compose.https.yml up -d --build
```

## Обновление базы

Flyway выполняет V1 и V2 до старта приложения, Hibernate только проверяет схему. Для прежней непустой схемы применяется baseline 0. Перед обновлением проверьте дубли `(product_id, store_id, price_date)` и неположительные цены. Миграция намеренно не удаляет конфликтующие записи. Если есть ошибка, сохраните данные и разберите причину до повторного запуска.

## Резервная копия и её проверка

```bash
sudo bash scripts/backup.sh
sudo bash scripts/check-backup.sh backups/ИМЯ_КОПИИ.dump
```

Вторая команда восстанавливает архив в новую временную БД, проверяет таблицу цен и удаляет только эту временную БД. Она не перезаписывает рабочую базу. Копии должны храниться также вне ВМ. Не выполняйте `docker compose down -v`: это удалит volume.

Перед обновлением сохраните исходники, `.env` в защищённом месте и текущие образы под отдельными тегами. Для возврата предыдущей версии используйте сохранённые образы и конфигурацию. Откат схемы или восстановление рабочей БД из архива — отдельная операция после оценки последующих изменений данных.

## Мониторинг

`/actuator/health` доступен без входа и показывает только общий статус. `/actuator/info`, `/actuator/metrics` и `/actuator/prometheus` требуют сессии ADMIN. `env`, `beans`, `configprops` не публикуются. Отдельные Prometheus и Grafana не входят в этот этап. Для диагностики используйте `docker compose logs --tail=100 backend` и состояние контейнеров.
