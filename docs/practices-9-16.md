# План и проектные решения для практик с 9 по 16

## Объём этапа

Исходная версия уже содержит каталог, выбор города, корзину, две стратегии сравнения, наборы, акции, историю цен и развёртывание через Docker. Новый этап добавляет защищённое управление ценами и уточняет требования, проектирование данных, архитектуру и эксплуатацию. Сохранённые корзины, избранное и персональные рекомендации остаются за пределами этапа.

## Требования и критерии приёмки

| Код | Требование | Проверка |
|---|---|---|
| F01 | Каталог, наборы, акции и сравнение доступны гостю | Публичные страницы и HTTP 200 |
| F02 | Администратор входит и завершает сессию | Верный пароль: 204; неверный: 401; после выхода ресурс закрыт |
| F03 | Менять цены может только ADMIN | Гость: 401; USER: 403 |
| F04 | Создание, чтение, изменение и удаление цены | 201, 200, 200 и 204 соответственно |
| F05 | Для пары товар/магазин за дату одна запись | Повторная запись: 409, включая конкурентные запросы через ограничение БД |
| F06 | Отрицательные цены, будущие даты и отсутствующие товары отклоняются | 400/404; запись в БД не появляется |
| F07 | Изменение корзины, города или стратегии сбрасывает старый расчёт | В интерфейсе требуется пересчёт |
| F08 | Обновление не удаляет существующие цены | Сравнение количества записей до и после миграции копии базы |
| N01 | Пароли не хранятся открытым текстом в БД | BCrypt, в JSON нет passwordHash |
| N02 | Запись защищена от CSRF | Без токена: 403 |
| N03 | Публичный вход работает по HTTPS | Доверенный сертификат, Secure cookie, HTTP перенаправляется |
| N04 | Интерфейс доступен на телефоне и с клавиатуры | Ширина 390 px, подписи полей, видимый фокус |
| N05 | После сбоя процесс восстанавливается | restart unless-stopped, healthchecks |
| N06 | Резервная копия пригодна для восстановления | pg_restore в отдельную временную БД |

N03 проверяется отдельно на сервере после выпуска сертификата. Наличие настроек в файлах само по себе не подтверждает успешную публикацию.

## Последовательность работ

1. Зафиксировать исходную версию и требования; сохранить исходники и БД.
2. Спроектировать пользователя, ограничения цен и миграции.
3. Реализовать сессии, роли и административный API.
4. Подключить форму управления и состояния ошибок; проверить мобильную версию.
5. Выполнить HTTP-тесты, сборку и проверку PostgreSQL.
6. Проверить миграции на копии серверной базы; выпустить сертификат и развернуть версию.
7. Зафиксировать результаты, снимки экранов и ограничения в отчёте.

Зависимости: шаг 3 опирается на 2; 4 — на 3; 6 — на 5 и резервную копию; отчёт фиксирует только выполненные проверки. Ответственность сохраняет роли первого отчёта: backend — Исаев Иса, frontend — София Головушкина, координация — Валерия Иванова, требования и модель данных — Всеволод Карцев. Это распределение зон ответственности, а не журнал фактически затраченного каждым участником времени.

Плановая оценка для команды: требования 2 ч, БД 3 ч, API и вход 5 ч, UI 3 ч, проверки 3 ч, развёртывание 3 ч, отчёт 3 ч. Оценки нужны для планирования и не выдаются за замер трудозатрат.

## Риски

| Риск | Мера |
|---|---|
| Дубли старых цен мешают UNIQUE | Проверка до миграции; остановка без автоматического удаления |
| Потеря базы при обновлении | Постоянный volume, pg_dump, восстановление копии |
| Пароль попал в репозиторий | .env исключён, права 600, в БД хеш |
| HTTP передаёт пароль открыто | HTTPS до публичного использования входа |
| Истёк короткий сертификат IP | Таймер продления дважды в сутки, проверка renew |
| Ошибка сети или несовместимая библиотека | Проверенная сборка, сохранённые предыдущие образы, откат |
| Цены устарели | Отображать дату; демонстрационный набор не считать актуальным каталогом сети |

## Выбор архитектуры

| Модель | Преимущества для проекта | Издержки |
|---|---|---|
| Монолитный backend | Одна сборка, транзакции в одной БД, простое развёртывание | Серверная часть масштабируется целиком |
| Микросервисы | Независимое масштабирование отдельных функций | Сетевая связность, несколько развёртываний, распределённая диагностика |
| Serverless | Оплата по вызовам, автоматическое масштабирование | Зависимость от платформы, холодный старт, работа с сессиями и PostgreSQL усложняется |

Выбран монолитный backend с разделением controller/service/repository. React поставляется отдельно как статические файлы. Три инфраструктурных контейнера не превращают приложение в микросервисную систему: бизнес-логика остаётся в одном Spring Boot процессе. Для команды из четырёх человек и учебной нагрузки эта схема требует меньше инфраструктуры.

Рост: сначала измерить время запросов, использовать индексы и вертикальные ресурсы; затем при подтверждённой нагрузке рассмотреть кэширование справочников и вынесение сессий в общее хранилище. Кэширование и микросервисы на этом этапе не реализованы и не нужны для доказательства базового сценария.
